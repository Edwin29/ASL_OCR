# Piper System Prompt Transport Work Packet

## Goal

Move production device guidance from the Windows SAPI side channel to WAV files synthesized by the server's configured Piper voice, transported through authenticated S0 endpoints, and serialized with document audio by one Device Runtime playback arbiter.

## In scope

- Maintain a named, versioned set of Korean system prompts for screen changes, capture hand-off, save/finalization, recoverable errors, scanner guidance, and the synthetic new-datapack catalog row.
- Synthesize fixed prompts and dynamic datapack titles into the shared `_system` pool with the same Piper instance used by the production S1 pipeline.
- Return device-scoped opaque title audio references and expose authenticated, path-confined WAV endpoints for fixed cues and title resources.
- Extend the Device Runtime HTTP audio adapter to fetch both reading-session resources and device-scoped system resources with the existing WAV size, digest, and format validation.
- Replace the production SAPI feedback path with a single playback arbiter shared by system prompts and reading snapshots.
- Define deterministic queue behavior: reading navigation and error/capture-complete cues may interrupt stale lower-priority prompts; catalog movement replaces stale catalog speech; duplicate active or queued cues are suppressed; no two WAV streams play concurrently.
- Preserve JSONL semantic feedback as diagnostic evidence and keep Windows SAPI only as an explicitly selected legacy diagnostic backend.

## Out of scope

- Raspberry Pi ALSA/PipeWire backend implementation.
- Live Android/UVC camera validation.
- Changing OCR/math-recognition accuracy or document speech wording.
- Persisting downloaded WAV files on the device.

## Acceptance

1. Fixed system prompts are generated by Piper and are non-empty PCM WAV resources in `_system`.
2. Catalog entries expose a device-scoped `s0-system-audio:` reference; another device cannot use that reference.
3. Missing/invalid API keys and malformed/cross-device references are rejected.
4. Device system and reading audio share exactly one `AudioPlaybackPort` instance.
5. Screen announcement precedes the initial catalog title; rapid catalog moves do not replay stale titles.
6. A navigation generation change interrupts prior playback and plays only the newest document audio.
7. Capture-complete and error prompts follow the defined priority and deduplication policy.
8. Device Runtime, Book Scanner, and Document Parser full regression suites remain green.

## Evidence

- Unit tests for synthesis/index reuse, path confinement, authentication, device scoping, fetch validation, queue ordering, priority interruption, deduplication, and generation replacement.
- Local composition integration test proving one player is used for both feedback and reading audio.
- Full suite results and a clean `git diff --check` for first-party files.
