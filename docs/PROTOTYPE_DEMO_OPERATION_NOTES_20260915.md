# 프로토타입 시연 운용 주의사항

## 최종 시연 플랫폼에 따른 적용 범위 정정

최종 시연은 Laptop 수동 실행이 아니라 **Pi4 전원 투입 후 자동 시작, 종료는 전원 차단**이다. 아래 PowerShell/Ctrl+C/앱만 재시작 절차는 Laptop 개발·진단용 기록이며 최종 사용자의 필수 조작 절차가 아니다. Pi에서는 cold boot 준비와 실제 전원 차단 후 cursor/outbox 복구, 부팅 CLEAR를 우선 검증한다. 전원 차단 전에 CONFIRM LONG/Ctrl+C가 반드시 수행된다고 가정하지 않는다. 상세 우선순위는 [Pi4 H4 이전 재평가](PI4_DEMO_PRE_H4_REASSESSMENT_20260915.md)를 따른다. 사용자는 Pi4·STM·PCA/서보가 모두 함께 꺼짐을 확인했다. 따라서 정상 시연은 전체 cold boot로 검증하고, 아래 첫 UP 재접속 절차는 앱만 재시작된 예외 상황의 우회로 남긴다.

## 채택한 범위

2026-09-15 사용자는 V3 재접속 후 조작 정상 작동을 확인하고, 무조작 재접속 및 첫 입력 소모를 완전 자동화하기보다 프로토타입 제약으로 기록하고 시연 주의사항으로 관리하는 방향을 제안했다. 이에 따라 해당 두 항목은 **알려진 프로토타입 운용 제약으로 수용**, 추가 자동화 구현은 보류한다. 원인이 해결됐거나 무조작 재접속 시험이 PASS라는 뜻은 아니다. Production V3-only 정책은 유지한다.

## 시연 시작 전

1. 서버 가동과 Laptop 연결을 확인하고, 현재 배포 hash에 맞는 실행기를 사용한다. 구버전 hash guard 실행기는 사용하지 않는다. Python 앱은 하나만 실행하고 Tera Term 등 COM9를 점유하는 프로그램은 닫는다.
2. STM·PCA·서보 전원 및 연결 상태를 준비하고, 앱을 시작한다. Catalog 음성이 들리는 것만으로 물리 입력 연결 완료로 판단하지 않는다.
3. host `HELLO,3`/`ACK,HELLO,3`와 STM `HOST CONNECTED (V3 EDGES)`, MODE 입력 수신을 확인한다. V2/legacy는 production 수용 대상이 아니다.
4. 연결 후 같은 READY의 음성·점자와 DOWN 해제 후 정지를 짧게 확인한다. 초기 blank FRAME을 STM이 해석했는지와 실제 전체 수납은 각각 확인한다.

## 앱만 재시작했을 때

보드가 이전 host 연결을 유지한 것으로 판단하면 입력이 없을 때 재협상을 시작하지 않는다. host가 COM을 재시도하는 동안 기다리는 것만으로 해결되지 않을 수 있다.

1. Catalog가 표시돼도 V3 연결이 확인되지 않으면 **UP을 짧게 한 번만** 누른다. 첫 입력은 연결을 깨우는 용도이며 정상 이동을 기대하지 않는다.
2. 다른 입력 없이 최대10초 관측한다. 이번 실제 시험에서는 ACK 재시도 실패 후 약2초에 V3로 재접속했지만 이 시간은 모든 환경의 보장값이 아니다.
3. V3/현재 MODE를 확인한 뒤 원하는 데이터팩 선택·CONFIRM을 새로 수행한다. 연결 유발 입력을 유효한 읽기 명령으로 세지 않는다.
4. V3가 확인되지 않으면 연속 버튼 입력·반복 재시작을 중단하고 로그와 상태를 확인한다. V2로 우회하거나 원인 확인 없이 flash하지 않는다.

위 절차는 **입력 유발 재접속**이다. 전원 단절/Bluetooth 장애 전반의 무인 자동 회복을 보장하지 않는다. 시연 중에는 가급적 검증된 앱 세션을 유지한다.

## 종료 및 셀 정리

- 셀을 수납해 마무리하려면 앱이 연결된 상태에서 **CONFIRM 길게 → 목록 복귀 → 실제 전체 수납 확인** 후 Ctrl+C 한 번으로 종료한다.
- Ctrl+C만으로 종료하면 현 구현은 CLEAR를 전송하지 않아 마지막 점자 상태가 남을 수 있다. 이는 이미 통과한 catalog CLEAR의 실패와 다르다. 종료 자동 CLEAR 기능은 이번에 추가하지 않았다.
- Ctrl+C 이후 프롬프트 복귀를 기다린다. 별도 종료 코드가 표시되지 않을 수 있다. 이번 계측에서 application.exit_code0/COM·audio close 정상 반환 및 Python 종료는 확인했으나 PowerShell native exit code는 null로 남았다.
- 첫 FRAME 앞부분 손실은 여전히 존재하며, 초기 MODE 이후 한 번 재송신하는 기존 완화로 수신됐다. 수납을 실제 확인하기 전에는 정상 적용으로 간주하지 않는다. 이 손실 자체가 해결됐다고 설명하지 않는다.

## 검증 상태와 재개 조건

V3-only 상태의 물리 reading, 입력 유발 재접속, 동일 cursor 복구 및 앱 자원 정리는 해당 run에서 확인됐다. 사용자 관측과 COM/STM 로그를 분리해 보존한다. H4의 live camera→새 두 spread→durable receipt→fresh READY→물리 읽기 전체 시험은 별도이며 이번 운용 제약 수용으로 자동 통과시키지 않는다.

무인 운용이 필요해지거나, 단일 입력 후에도 반복적으로 연결되지 않거나, 시연에서 첫 입력 소모가 허용되지 않으면 종료 감지/재협상 자동화 작업을 다시 연다. 현재는 이 범위에 대한 추가 제품 수정을 하지 않는다.
