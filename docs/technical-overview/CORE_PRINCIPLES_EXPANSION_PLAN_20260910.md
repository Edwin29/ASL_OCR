# 핵심 원리 해설 보강 계획

상태: **2026-09-10 사용자 진행 지시에 따라 완료**. 계획 수립 시에는 미착수였으며 이후 용어 병기를 먼저 마치고 아래 순서로 실행했다. [선정표](CORE_PRINCIPLES_SELECTION.md) → [근거 카드](CORE_PRINCIPLES_EVIDENCE_CARDS.md) → [배치 설계](CORE_PRINCIPLES_BLUEPRINT.md) → [최종 문서](../ASL_OCR_TECHNICAL_OVERVIEW.md) → [검증과 교정](CORE_PRINCIPLES_VERIFICATION.md). 아래 내용은 실행에 사용한 원래 계획을 보존한다.

선행 작업인 [독자 피드백 반영](READER_FEEDBACK_REVISION_20260910.md) 후 작성했다. 목표는 구현 명칭을 더 많이 설명하는 것이 아니라, 결과를 결정하는 소수의 원리를 선정하고 필요성·효과·한계를 근거와 함께 이해시키는 것이다.

## 1. 선정 기준부터 확정

후보마다 다음 질문에 답할 수 있을 때 핵심 해설에 포함한다.

1. 사용자가 겪는 어떤 실패나 어려움을 다루는가?
2. 실제 현재 실행 경로의 어디에서 사용되는가?
3. 없거나 다르게 동작할 때 결과가 어떻게 달라지는가?
4. 코드·테스트·실험 중 무엇으로 그 설명을 뒷받침하는가?
5. 효과가 확인된 범위와 아직 검증하지 못한 한계는 무엇인가?

현재 코드에서 관찰되는 효과, 문서에 명시된 채택 이유, 성능 실험으로 입증된 우위는 별개로 표시한다. 채택 이유가 확인되지 않으면 개발자의 의도로 단정하지 않는다. 비교 실험이 없으면 ‘다른 방식보다 우수하다’고 쓰지 않는다.

산출물: 후보 선정표(포함·보류·제외와 근거). 완료 전에는 심화 본문을 작성하지 않는다.

## 2. 우선순위별 조사 후보

| 순서 | 후보 | 조사할 질문 | 사용할 근거의 시작점 | 예상 독자 산출물 |
|---|---|---|---|---|
| 1 | 수식 구조 트리(AST) | 실제 생성·소비 지점은 어디인가? 문자열만 보관하는 것과 어떤 정보 차이가 있는가? 음성·점자·탐색에서 어떤 역할을 하는가? 해석 상태와 원문 정확성은 왜 다른가? | PASS2 A 카드, latex_ast, flattening, speech/math_rules, braille/math_translator, 대응 테스트 | 같은 작은 수식을 따라가는 입력→구조→두 출력 비교와 한계 |
| 2 | 페이지 해석과 읽기 순서 | 모델 결과를 어떤 규칙으로 글·수식·표·문제 단위로 바꾸는가? 위치·순서가 충돌하거나 누락될 때 무엇을 잃는가? | VL adapter, vl_page_ir, table_html, problem_units, flattening, PASS3 변환표 | 한 페이지의 영역→중간 표현→읽기 항목 추적 |
| 3 | 페이지 중복 관련 처리 | ‘중복’이 촬영 중복, 좌우 추출 겹침, 재전송 중복, 읽기 항목 중복 중 무엇인가? 각 단계의 근거와 실패 조건은 무엇인가? | opaque_identity/page_change/engine, spread_extraction, delivery/V4, flattening, 해당 실험 기록 | 혼동하기 쉬운 네 종류를 분리한 판단 흐름과 작은 반례 |
| 4 | 단계별 검증의 목적 | 검사마다 어떤 잘못된 결과가 다음 단계로 넘어가는 것을 막는가? 통과해도 보장하지 못하는 것은 무엇인가? | source/decode, spread_preparer, V4 hash/receipt, S1 validation/assembler, audio/FRAME parser, PASS3 실패표 | 검사→막는 실패→통과의 의미→남은 한계 표 |
| 5 | 상태와 완료를 분리하는 처리 | 중복 명령·재시작·오래된 음성·최신 점자 상태를 어떻게 다루는가? 자료 저장과 실물 출력의 보장이 어디서 끊기는가? | S0 progress/receipt, audio epoch, serial latest FRAME, firmware/PCA, PASS6 교정 | 한 번의 입력과 응답 유실·재진입을 비교하는 사례 |

우선순위3의 ‘중복 페이지 산출’은 한 문제로 묶지 않는다. 원문의 요구가 뜻할 수 있는 여러 경계를 먼저 나누고, 본문에 필요한 항목만 선정한다. 검증된 threshold나 protocol을 변경하는 계획은 아니다.

## 3. 근거 카드 작성 후 설명 구조 설계

선정한 각 원리에 대해 문제, 입력, 사용하는 정보, 처리, 판단, 출력, 실패, 다음 단계, 코드 위치, 실제 검증 범위를 한 장의 분석 카드로 만든다. 의도·효과·성능 우위를 구분하고 설명이 추정에 기대는 부분은 미확인으로 남긴다.

그다음 기존 문서의 §4·§6에 배치할 해설과 §7의 대표 사례를 설계한다. 각 원리에는 ‘이전 단계의 무엇을 받아 어떤 판단을 거쳐 다음 단계의 무엇을 만드는지’를 포함한다. 용어 설명만 늘어나거나 같은 절에 파일·클래스 목록이 쌓이는 구성은 제외한다.

완료 조건: 모든 핵심 주장에 근거가 연결되고, 예제의 값·상태·실패 분기를 확인할 수 있어야 한다. 이 설계가 끝난 뒤에만 본문을 보강한다.

## 4. 향후 본문 작성·검증 순서

1. 문제→선택한 처리→판단→결과→한계 순으로 해설한다. 확인하지 못한 개발 의도나 비교 우위를 넣지 않는다.
2. 한 페이지 또는 작은 수식의 동일 입력을 재사용해 단계 간 변환을 연결한다. 재현 예제와 실제 H1 관측을 명시적으로 구분한다.
3. 새 주장·도식을 코드와 테스트에 다시 대조하고 오류 목록을 먼저 작성한 뒤 교정한다.
4. 모든 Mermaid를 실제 렌더링하고 한글·배치·가독성을 확인한다. 링크와 source 해시도 검사한다.
5. 처음 읽는 독자가 코드명 없이 원리·필요성·실패 시 동작을 설명할 수 있는지 문서에서 점검한다.

## 5. 범위와 완료 조건

대상은 문서와 필요한 격리 예제다. 코드 변경, architecture 개선, 신규 성능 벤치마크, 모델 교체, 하드웨어 시험은 이 계획에 포함하지 않는다. 기존 근거로 답할 수 없는 질문은 추가 진단 후보로 남긴다.

최종 완료는 선정한 핵심 원리마다 필요성·실제 사용처·입출력·판단·검증 이유·한계가 이해 가능한 사례와 함께 설명되고, 근거와 실제 렌더링 검증이 연결된 상태다. 이 파일은 실행 계획을 보존한 문서이고 실제 완료 결과는 상단의 산출물에서 확인한다.
