# book-scanner

문제집 페이지를 개조 휴대폰 카메라 + Raspberry Pi로 스캔해 `document-parser`에
input으로 넘기는 파이프라인. 휴대폰은 카메라 센서 역할만 하고, 페이지 검출/촬영
판단/보정/저장/송신은 전부 Raspberry Pi가 담당한다 (역할 분리 배경은
`problem_book_scanner_agent_context.md`, 전체 로드맵은
`problem_book_scanner_roadmap.md` 참고).

## 지금 이 저장소가 하는 것

프레임 안에서 페이지로 보이는 사각 영역을 찾고(`measure.py`), 그 기하가 "지금
촬영해도 되는 상태"인지 판정한다(`judge.py`). 실제 배치에서는 카메라 거치대 +
책받침 배치 가이드 + 인공조명이 각도·거리·빛반사·그림자를 물리적으로 통제하므로,
열악한 조건에서의 인식은 다루지 않는다. 남은 일은 딱 하나: **주어진 앵글에 사각형
페이지가 정확히 들어왔는지** 판정하고, 아니라면 거부 사유를 반환하는 것
(사유는 이후 리셋 비프음 트리거 등 외부 로직이 사용할 수 있는 상태값 —
`RejectReason`).

```
src/book_scanner/capture/
  types.py     # PageGeometry(측정 결과), CaptureVerdict/RejectReason(판정 결과)
  measure.py   # 순수 측정: 이미지 -> PageGeometry | None (OpenCV, 판단 로직 없음)
  judge.py     # 순수 판정: PageGeometry | None -> CaptureVerdict (OpenCV 없음)
src/book_scanner/correct/
  types.py      # Corners, CorrectionMetadata(원본/보정본 해시·촬영 식별자)
  perspective.py # 순수 워프: 이미지 + Corners -> 보정된 배열 (파일 I/O 없음)
  pipeline.py    # 오케스트레이션: 해시 검증 + 원자적 파일 쓰기 + 메타데이터 저장
```

측정과 판정을 분리해 둔 이유: 검출 알고리즘(현재는 Canny+컨투어+`minAreaRect`)을
나중에 바꾸더라도 판정 로직을 건드릴 필요가 없게 하기 위함. 페이지 판형(A4 등)이나
흰색 여부는 가정하지 않는다 — 순전히 테두리 기하로만 판단한다. `correct/`도 같은
원칙으로 나눴다: 워프 수학(`perspective.py`)과 저장/해시/메타데이터 책임
(`pipeline.py`)이 분리돼 있다.

## 실행

```bash
pip install -e .
python -m pytest tests/unit -q
```

fixture를 다시 만들어야 하면 (원본 사진이 바뀌었을 때만):

```bash
python tests/fixtures/generate_fixtures.py
```

## 발견 및 수정한 버그

- **해상도 의존성 (수정됨)**: `measure.py`가 원래 입력 프레임에 직접 고정
  픽셀 크기의 Canny/blur/dilate 커널을 적용했다. `tests/fixtures/`용
  ~1200px 사진에서는 잘 맞았지만, 실제 폰 촬영 해상도(3000~4000px)에서는
  페이지 외곽선이 하나로 안 닫히고 잘게 쪼개져 엉뚱한 내부 블록을 페이지로
  오인했다(원격 테스트 중 실제 폰 사진으로 발견 — `area_ratio 0.998`이어야
  할 사진이 `0.018`로 나옴). 내부적으로 이미지를 downscale해서 검출하고
  결과 좌표를 원본 해상도로 되돌리는 방식으로 수정했다(`_WORKING_MAX_DIM`).
  fixture(~1200px)로만 검증하고 실제 촬영 해상도로는 테스트를 안 했던 게
  원인이었다 — `python -m pytest`만으로는 안 잡히고, 실제 크기 이미지로
  돌려봐야 드러나는 종류의 버그였다.

- **OUT_OF_FRAME 오탐 (수정됨)**: 원래 `judge.py`가 `minAreaRect`로 적합(fit)한
  사각형의 꼭짓점(`corners`)이 프레임 경계 근처인지로 OUT_OF_FRAME을
  판정했다. 하지만 fit된 사각형의 꼭짓점은 실제 컨투어가 아니라 그걸 감싸는
  최소 회전 사각형의 수학적 계산값이라, 크고 살짝 회전된 블록의 경우 실제
  검출된 내용물엔 여백이 있어도 fit된 사각형 꼭짓점만 계산상 프레임 밖으로
  나가는 경우가 있었다(원격 테스트 중 여백이 있어 보이는 실사진이
  OUT_OF_FRAME으로 잘못 거부되어 발견). `PageGeometry`에
  `touches_frame_edge` 필드를 추가해 fit된 사각형이 아니라 원본 컨투어
  좌표가 실제로 프레임 경계에 닿는지를 직접 검사하도록 바꿨다. 실사진
  하나(`20260825_170944.jpg`, area_ratio 0.268)가 이 수정으로 거부에서
  허용으로 바뀐 걸로 확인했다.

## 테스트 데이터에 대한 메모 (실측 중 발견한 것)

`tests/fixtures/real/`의 실사진 6장은 아직 물리적 거치대/책받침 가이드가 없는
상태에서, 나무 책상 위에 펼친 대학물리학2(Cengage) 교재를 손으로 찍은 것이다
(EBS 수능특강 실물은 없어 대용으로 사용). 이 사진들로 직접 측정해 본 결과를
정직하게 남긴다:

- 나무 책상 배경 자체에 엣지가 충분히 많아서, 단순 Canny+컨투어 검출이 "페이지만"
  깔끔히 분리하지 못하고 사진 프레임 대부분(때로는 거의 전체)을 하나의 컨투어로
  잡는 경우가 잦다. 6장 중 다수가 `area_ratio` 0.77~0.998로 측정됐다 — 이는 실제
  거치대/배경 통제가 없는 현재 조건의 한계이지, 알고리즘이 실제 배치 조건에서도
  이럴 것이라는 뜻은 아니다. 실제 지그가 생기면 재측정이 필요하다.
- 그래서 `tests/fixtures/generated/`의 "고의로 회전/훼손한" 케이스들은 실사진
  6장 중 하나를 원본 그대로 하나의 "내용 블록"으로 취급해, 더 큰 캔버스 위에
  회전/축소/왜곡해서 배치하는 방식으로 만들었다 (`generate_fixtures.py`). 이렇게
  하면 배경-페이지 분리 노이즈와 무관하게 "회전이 커지면 reject된다" 같은 기대
  결과가 결정적으로 나온다.
- 원본 사진 중 하나(`20260825_170921.jpg`)는 촬영 당시 이미 프레임 가장자리까지
  내용이 꽉 차 있어서, 별도 가공 없이도 자연스러운 `OUT_OF_FRAME` 사례로 쓴다.
- 알려진 한계: 완만한 사다리꼴 원근 왜곡(`perspective_warp.jpg`)은 현재의
  `minAreaRect` 각도/면적비 기반 판정으로 안정적으로 걸러지지 않는다
  (`tests/unit/test_judge.py`의 관련 테스트에 이유를 남겨 뒀다). 실제 지그가
  카메라 시야각 자체를 고정하므로 우선순위는 낮다고 보고, 이번 범위에서는
  구현하지 않았다.

## 판정 임곗값

`judge.py`의 `JudgeThresholds` 기본값은 위 실사진/생성 fixture로 1차 보정한
값이며, **물리적 거치대·책받침 가이드 확정 전 잠정값**이다. 실제 지그가 만들어지면
그 조건에서 다시 측정해 갱신해야 한다.

## Stage 6 (페이지 보정 및 스캔 산출물 생성) 진행 상황

`problem_book_scanner_roadmap.md`의 Stage 6에 해당. `correct/` 모듈이 완료
조건 중 하드웨어 없이 채울 수 있는 부분을 구현한다:

- 네 꼭짓점 기반 원근 보정 (`perspective.py`)
- 출력 크기는 검출된 사각형 자체의 실측 크기 그대로 — 업스케일로 해상도를
  위장하지 않음
- 원본 파일은 절대 쓰지 않음 (읽기 전/후 sha256 비교로 실제로 검증)
- 보정본을 원본과 분리 저장, 각각 sha256 해시 + 촬영 식별자(`capture_id`)를
  메타데이터 JSON에 기록 (`pipeline.py`의 `CorrectionMetadata`)
- 저장은 임시 파일 쓰기 → `os.replace`로 원자적 교체 — 중간에 실패해도
  불완전한 파일이 정상 산출물 자리에 남지 않음 (`test_failed_write_leaves_no_partial_output`로 검증)

로드맵이 명시한 대로, 이 Stage는 원래 Stage 2(렌즈·촬영 평면 교정)가 끝난
뒤를 전제로 한다. Stage 2는 물리적 거치대가 있어야 하므로, 지금은 건너뛰어
아직 안 된 것들: **렌즈 왜곡(방사 왜곡) 보정**, **네 꼭짓점 자동 검출**
(현재는 사람이 사진을 보고 좌표를 지정 — `capture/measure.py`의 자동 검출은
이 세션에서 반복적으로 신뢰성 문제가 발견돼 아직 못 씀), 실질 300dpi 충족
여부의 정식 검증.

### 실측 검증: document-parser 파이프라인 통합 테스트

실제 EBS 수능특강 수학Ⅰ 30페이지를 태블릿 PDF 뷰어 화면으로 촬영 →
`perspective_correct.py`로 보정(사람이 좌표 지정) → document-parser의
실제 OCR 파이프라인(PaddleOCR-VL)에 투입 → 기존 레퍼런스 렌더
(`ebs_2027_math1_p030.png`)와 비교한 결과:

- 노드 수(22), TEXT/UNKNOWN 분포(18/4), reading_order 길이(10), 문제 단위
  인식(4개) **전부 일치**
- 22개 노드 중 15개는 텍스트까지 완전 일치, 나머지 7개는 헤더/푸터 순서
  뒤바뀜(내용은 정확) 또는 LaTeX 지수 표기(`x` vs `{x}`) 차이뿐 —
  의미 있는 인식 오류 0건

원근 보정만 정확하면(자동 검출 여부와 무관하게), document-parser는 촬영된
사진에 대해 기존 PDF 렌더 이미지와 사실상 동일한 결과를 낸다는 것을 확인.

## 이번 범위에서 하지 않은 것

- 휴대폰-Pi 실시간 연결/프리뷰 스트리밍 (하드웨어 없음)
- 렌즈 왜곡(방사 왜곡) 보정, 네 꼭짓점 자동 검출 (위 Stage 6 절 참고)
- 300dpi 해상도 적합성의 정식 검증 (Stage 2 교정 의존)
- 이미지 방향(EXIF) 정규화
- 실제 비프음/하드웨어 트리거 (거부 사유를 상태값으로 제공하는 데까지만)
- 메인 서버 송신, 실패 시 로컬 보존/재시도
- Pi 자원 제약을 고려한 프리뷰 프레임 관리(오래된 프레임 폐기 등)

전부 로드맵의 이후 단계이며, 요청받은 뒤 진행한다.
